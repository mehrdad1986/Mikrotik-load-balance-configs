Topology & Design Goal

Two independent internet lines share the load. Every new connection is hashed to one WAN and stays there for its lifetime. If a WAN dies, its connections fail over automatically.

InterfaceRoleRouter IPGateway
ether1WAN1192.168.2.100/24192.168.2.1
ether2WAN2192.168.0.100/24192.168.0.1
bridge2 (ether4+ether5)LAN192.168.10.1/24—
Design Goal PCC assigns each new TCP/UDP connection to a WAN once, using a hash. All subsequent packets of that connection follow the same WAN — preventing broken sessions (banking, video calls, VPNs). The two routing tables (to-WAN1, to-WAN2) enforce this per-connection path.

The Reading Method

Every mangle rule is a sentence. Read it left to right as a chain of conditions and actions. The condition at the end is the gate — it must be true before the action fires.

Example rule decoded token by token:

add chain=prerouting action=mark-routing new-routing-mark=to-WAN1 \
    passthrough=no connection-mark=WAN1-conn
chain=prerouting action=mark-routing new-routing-mark=to-WAN1 passthrough=no connection-mark=WAN1-conn (GATE)
chain=prerouting"In the prerouting chain..." — runs before the routing decision is made.
action=mark-routing"...apply a routing mark to this packet..." — stamps a per-packet label the routing engine reads.
new-routing-mark=to-WAN1"...the mark to apply is called 'to-WAN1'..."
passthrough=no"...and stop processing further mangle rules after this." — the packet's fate is decided.
connection-mark=WAN1-conn"...BUT ONLY IF this packet's connection is already tagged 'WAN1-conn'." — the gate, evaluated last.
Plain English When a packet arrives in prerouting: check if it belongs to a connection already decided to use WAN1. If yes, stamp it "to-WAN1" and stop. If no, skip this rule entirely.
3

How PCC Hashing Actually Works

PCC is a deterministic hash function built into RouterOS. It takes fields from the packet, computes a number, divides by the total bucket count, and checks the remainder. Same inputs always produce the same bucket — that's what keeps a connection on one WAN.

The Hash Formula

Input fields:src-IP + dst-IP + src-port + dst-port
Hash function:internal hash -> integer N
Bucket formula:N mod total_buckets = remainder
Rule 2/0 catches:remainder = 0 -> WAN1-conn
Rule 2/1 catches:remainder = 1 -> WAN2-conn
Example A:10.0.0.5:54321 -> 8.8.8.8:443=>hash=4, 4 mod 2 = 0 -> WAN1
Example B:10.0.0.7:49152 -> 1.1.1.1:80=>hash=7, 7 mod 2 = 1 -> WAN2

Classifier Modes Compared

ClassifierFields HashedBest ForWeakness
src-addressSource IP onlyMany different client IPsOne heavy user monopolizes a WAN
dst-addressDestination IP onlySpreading across many serversAll traffic to one server goes one WAN
both-addressesSrc IP + Dst IPBalanced per client-server pairSame client to same server always same WAN
both-addresses-and-portsSrc IP + Dst IP + Src Port + Dst PortBest balance — each connection is uniqueSlightly more CPU (negligible on hEX)
Why both-addresses-and-ports is recommended A single client opening 10 connections to the same server (e.g. a browser loading a webpage) will get those connections split across both WANs, because each connection has a different source port. With src-address alone, all 10 connections from that client would always go to the same WAN.

The N/M Syntax Decoded

both-addresses-and-ports:2/02 = total number of buckets (= number of WANs). 0 = the bucket index this rule catches (0-indexed). So: hash mod 2 == 0.
both-addresses-and-ports:2/1Same hash, same total (2), but catches bucket index 1. Together, 2/0 + 2/1 = 100% of connections.
:3/0, :3/1, :3/2For 3 WANs: three rules, each catching one third of connections.
Why the split is "roughly" 50/50 The hash distributes statistically, not perfectly. With 2 clients you might get an uneven split. With 100 clients you'll be very close to 50/50. PCC is a statistical load balancer, not a strict round-robin.

Connection Mark vs Routing Mark vs Routing Table vs VRF

These four concepts are often confused. They are distinct layers that work together in sequence.

Connection Mark

Stored in conntrack (the connection tracking table). Persists for the entire lifetime of a connection. Set once when the connection is new. All packets of that connection can read it. Example: WAN1-conn.

Routing Mark

A per-packet label stamped in mangle. Lives only while the packet is being processed — not stored anywhere. Tells the routing engine "look in this specific routing table." Example: to-WAN1.

Routing Table

A named set of routes. The routing engine consults the table whose name matches the packet's routing mark. Contains its own default gateway. Example: table to-WAN1 has gateway 192.168.2.1.

VRF (Virtual Routing & Forwarding)

A full network isolation layer — separate routing table plus separate interface binding. Much heavier than a simple routing table. PCC does not use VRF; it uses lightweight named routing tables with fib.

New packet -> mangle prerouting
↓
PCC hash -> mark-connection (stored in conntrack forever)
↓
Read connection mark -> mark-routing (stamped on this packet only)
↓
Routing engine reads routing mark -> looks up matching routing table
↓

gateway 192.168.2.1

Phase 1 — Interface Lists, LAN IP, DHCP, DNS

Foundation layer: name the router, group interfaces, build the LAN bridge, assign IPs, and configure DHCP and DNS for LAN clients.

/system identity
set name="hEX-PCC-DualWAN"

/interface list
add name=WAN
add name=LAN

/interface list member
add list=WAN interface=ether1
add list=WAN interface=ether2

/interface bridge
add name=bridge2

/interface bridge port
add bridge=bridge2 interface=ether4
add bridge=bridge2 interface=ether5

/interface list member
add list=LAN interface=bridge2

/ip address
add address=192.168.2.100/24  interface=ether1  comment="WAN1"
add address=192.168.0.100/24  interface=ether2  comment="WAN2"
add address=192.168.10.1/24   interface=bridge2 comment="LAN"

/ip dns
set servers=1.1.1.1,8.8.8.8 allow-remote-requests=yes

/ip pool
add name=lan-pool ranges=192.168.10.100-192.168.10.250

/ip dhcp-server
add name=dhcp-lan interface=bridge2 address-pool=lan-pool lease-time=12h disabled=no

/ip dhcp-server network
add address=192.168.10.0/24 gateway=192.168.10.1 dns-server=192.168.10.1,1.1.1.1
interface list WAN/LANNamed groups. Firewall rules reference the group, not individual ports — add a new WAN port by updating the list, not every rule.
bridge2 (ether4+ether5)Merges two physical ports into one Layer-2 domain. The LAN IP is bound to the bridge, not a port — so it serves all bridge members simultaneously.
allow-remote-requests=yesWithout this, only the router itself can use the configured DNS servers. LAN clients sending queries to 192.168.10.1 would get no response.
lan-pool: .100-.250151 addresses for DHCP. Addresses .2-.99 are free for static assignments (servers, printers, etc.).

Phase 2 — Routing Tables & Main Default Routes

Create the two custom routing tables that PCC-marked traffic will use, then add default routes to the main table for non-PCC traffic and failover.

/routing table
add name=to-WAN1 fib
add name=to-WAN2 fib

/ip route
add dst-address=0.0.0.0/0 gateway=192.168.2.1 distance=1 check-gateway=ping comment="main primary WAN1"
add dst-address=0.0.0.0/0 gateway=192.168.0.1 distance=2 check-gateway=ping comment="main backup WAN2"
fib"Forwarding Information Base" — required in RouterOS 7 to make a named table active for actual packet forwarding, not just route storage.
distance=1 / distance=2Lower distance = higher priority. The distance=2 route is invisible to the routing engine while distance=1 is alive. It activates automatically when distance=1 fails.
check-gateway=pingRouterOS continuously pings the gateway. Two consecutive failures (~20-30s) marks the route inactive, triggering automatic failover to the backup distance=2 route.
Tip — Per-Table Failover Each custom table also needs its own backup route (added in Phase 6). The main-table routes here only cover traffic that bypassed PCC entirely (e.g. router-originated traffic before Phase 7 rules exist, or traffic that matched no mangle rule).

Phase 3 — NAT (Masquerade)

LAN devices use private IPs that don't exist on the internet. NAT rewrites the source address to the router's WAN IP so replies can find their way back.

/ip firewall nat
add chain=srcnat out-interface=ether1 action=masquerade comment="NAT WAN1"
add chain=srcnat out-interface=ether2 action=masquerade comment="NAT WAN2"
chain=srcnatFires just before a packet leaves the router — modifies the source address.
out-interface=ether1Only applies to packets actually exiting through ether1. The second rule independently handles ether2.
action=masqueradeAutomatically uses whatever IP is currently assigned to that interface — works even if the WAN IP changes (DHCP from ISP).
Why Two Separate Rules A single masquerade rule without out-interface would use the "current" primary IP regardless of which WAN the packet actually left through — breaking return traffic on the non-primary WAN. Each interface must have its own explicit rule.

Phase 4 — PCC Connection Marking

This is the decision step. A brand-new connection is hashed once and tagged with a connection mark that persists in conntrack for the connection's entire lifetime.

/ip firewall mangle

# Bypass: don't re-classify already-running connections
add chain=prerouting connection-state=established \
    action=accept passthrough=yes comment="skip established"

add chain=prerouting connection-state=related \
    action=accept passthrough=yes comment="skip related"

# Bypass PCC entirely for local/private destinations
add chain=prerouting dst-address-list=no-pcc \
    action=accept passthrough=yes comment="no PCC for local traffic"

# PCC hash - only fires on NEW connections without an existing connection-mark
add chain=prerouting connection-state=new connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:2/0 \
    action=mark-connection new-connection-mark=WAN1-conn \
    passthrough=yes comment="PCC bucket 0 -> WAN1"

add chain=prerouting connection-state=new connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:2/1 \
    action=mark-connection new-connection-mark=WAN2-conn \
    passthrough=yes comment="PCC bucket 1 -> WAN2"
connection-state=established / relatedTraffic belonging to a connection that's already running (or a helper connection like FTP data) skips re-hashing entirely — its connection-mark was already set when it was new.
dst-address-list=no-pccA pre-built address list (RFC1918 ranges, the router's own subnets, etc.). Traffic to these destinations should always exit locally — accepted with no mark.
connection-state=newGate: only fresh connections reach the hash. This is what makes PCC "per-connection" instead of "per-packet" — the decision happens exactly once.
connection-mark=no-markExtra safety gate — ensures a connection that somehow already has a mark isn't re-hashed and potentially reassigned to a different WAN mid-session.
action=mark-connectionWrites the mark into conntrack (not just this packet). Every future packet of this connection will carry connection-mark=WAN1-conn automatically, with zero extra hashing.
passthrough=yesAllow the packet to continue to the next mangle rule — because Phase 5 (mark-routing) still needs to process this same packet.
Plain English If this connection is brand new and has never been marked before: hash it. If the hash lands on bucket 0, tag the connection "WAN1-conn" forever. If bucket 1, tag it "WAN2-conn" forever. Either way, keep processing — the routing mark still needs to be set.
Order Matters These rules must appear before any general "accept" rule and after the established/related/no-pcc bypass rules. Mangle rules are evaluated top-to-bottom — a misplaced PCC rule can re-hash traffic that should have bypassed it.

Phase 5 — Routing Marking

Now every packet (new or returning) carries a connection-mark. This phase translates that connection-mark into a per-packet routing-mark that the routing engine can act on.

/ip firewall mangle
add chain=prerouting connection-mark=WAN1-conn \
    action=mark-routing new-routing-mark=to-WAN1 \
    passthrough=no comment="route WAN1-marked conns via to-WAN1 table"

add chain=prerouting connection-mark=WAN2-conn \
    action=mark-routing new-routing-mark=to-WAN2 \
    passthrough=no comment="route WAN2-marked conns via to-WAN2 table"
connection-mark=WAN1-connGate: reads the persistent conntrack mark set in Phase 4 — this rule fires for every packet of that connection, forever, not just the first one.
action=mark-routingStamps a temporary per-packet label — exists only for the duration this packet is inside the router.
new-routing-mark=to-WAN1The name must exactly match the routing table created in Phase 2 (/routing table add name=to-WAN1).
passthrough=noThis packet's classification is complete — stop processing further mangle rules for it.
Why Two Separate Mangle Phases? Phase 4 decides once per connection (expensive hash, but only computed on the first packet). Phase 5 re-applies every packet (cheap lookup, no hashing) by simply reading the stored connection-mark. Splitting it this way means the CPU-heavy hash never runs more than once per connection.

Phase 6 — Policy Routes for Marked Traffic

The routing-mark set in Phase 5 tells the routing engine which table to consult. Each table needs its own default gateway — and its own backup route for failover.

/ip route
add dst-address=0.0.0.0/0 gateway=192.168.2.1 routing-table=to-WAN1 \
    distance=1 check-gateway=ping comment="WAN1 table primary"
add dst-address=0.0.0.0/0 gateway=192.168.0.1 routing-table=to-WAN1 \
    distance=2 check-gateway=ping comment="WAN1 table failover via WAN2"

add dst-address=0.0.0.0/0 gateway=192.168.0.1 routing-table=to-WAN2 \
    distance=1 check-gateway=ping comment="WAN2 table primary"
add dst-address=0.0.0.0/0 gateway=192.168.2.1 routing-table=to-WAN2 \
    distance=2 check-gateway=ping comment="WAN2 table failover via WAN1"
routing-table=to-WAN1This route only exists inside the to-WAN1 table — invisible to the main table and to the to-WAN2 table. Packets only see it if their routing-mark matches.
distance=1 (primary)Normal path: WAN1-marked traffic always exits via ether1's gateway.
distance=2 (failover)If ether1's gateway stops responding to ping, this route activates — WAN1-marked connections now exit through WAN2 instead of dying.
Packet routing-mark = to-WAN1
↓
Look up table "to-WAN1"
↓
Gateway 192.168.2.1 alive?
YES -> exit ether1 (distance 1)
Gateway 192.168.2.1 dead?
YES -> exit ether2 via WAN2 (distance 2)
Best Practice This cross-failover design means a WAN1-marked connection surviving a WAN1 outage will actually egress through WAN2's physical interface — but NAT (Phase 3) still correctly masquerades it because masquerade rules key off out-interface, not routing-mark.
Caveat — Asymmetric Routing During Failover While failed over, both WAN1-marked and WAN2-marked connections may briefly share ether2's bandwidth. This is expected and acceptable — it's a temporary degraded state, not a misconfiguration.

Phase 7 — Router-Originated Traffic

Everything so far only handles traffic passing through the router (prerouting chain). Traffic the router itself generates — DNS lookups, NTP, ping, ROS updates — uses the output chain instead, which needs its own PCC rules.

/ip firewall mangle
add chain=output connection-state=established action=accept passthrough=yes
add chain=output connection-state=related action=accept passthrough=yes

add chain=output connection-state=new connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:2/0 \
    action=mark-connection new-connection-mark=WAN1-conn passthrough=yes

add chain=output connection-state=new connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:2/1 \
    action=mark-connection new-connection-mark=WAN2-conn passthrough=yes

add chain=output connection-mark=WAN1-conn \
    action=mark-routing new-routing-mark=to-WAN1 passthrough=no
add chain=output connection-mark=WAN2-conn \
    action=mark-routing new-routing-mark=to-WAN2 passthrough=no
chain=outputFires only for packets whose source is the router itself — never for LAN-to-internet traffic (that's prerouting).
(identical hash + mark logic)Mirrors Phases 4-5 exactly, so the router's own connections (e.g. a DNS query it sends to 8.8.8.8) are load-balanced the same way LAN traffic is.
Why This Is Easy to Forget Without these output-chain rules, router-originated traffic (DNS resolution, NTP sync, package update checks) silently falls through to the main routing table's default route — always using WAN1 (distance=1), even if WAN1 is degraded but not fully down. This can cause DNS timeouts that look like a LAN problem but are actually a router self-traffic problem.

Phase 8 — Disable FastTrack

FastTrack is a RouterOS performance feature that lets established connections bypass the firewall and mangle chains entirely after the first few packets. This directly breaks PCC.

/ip firewall filter
:if ([:len [find where action=fasttrack-connection]] > 0) do={
    disable [find where action=fasttrack-connection]
    :log warning "FastTrack rule found and disabled - required for PCC to function"
} else={
    :log info "No FastTrack rule present - OK"
}
:if ([:len [find ...]] > 0)RouterOS scripting: checks whether any firewall filter rule with action=fasttrack-connection exists, in case one was added by default configuration or a previous script.
disable [find where ...]Disables (does not delete) the rule — safer than removing it, and reversible if PCC is ever abandoned.
Critical — This Is Not Optional FastTrack marks a connection after its first few packets and then routes all subsequent packets through a fast kernel path that skips mangle entirely. Since PCC's routing-mark is applied in mangle, a fast-tracked connection would silently ignore its assigned WAN and always use the main table's default route. Symptom: PCC "appears to work" for the first second of a connection, then traffic mysteriously shifts to WAN1 only. Always verify FastTrack is disabled after any factory-default script runs (RouterOS often ships a default fasttrack rule in /ip firewall filter).

Netwatch — Accelerating Failover

check-gateway=ping alone takes roughly 20-30 seconds to detect a dead gateway. Netwatch can detect failure faster and immediately flush stale connections so they re-hash onto the surviving WAN instead of hanging.

check-gateway=ping only

~20-30s

detection + route switch delay

check-gateway=ping + Netwatch

~5-10s

faster detection, connections flushed immediately

/tool netwatch
add host=192.168.2.1 interval=5s timeout=1s \
    up-script=":log info \"WAN1 gateway UP\"" \
    down-script=":log warning \"WAN1 gateway DOWN - flushing WAN1 connections\"; /ip firewall connection remove [find where connection-mark=WAN1-conn]"

add host=192.168.0.1 interval=5s timeout=1s \
    up-script=":log info \"WAN2 gateway UP\"" \
    down-script=":log warning \"WAN2 gateway DOWN - flushing WAN2 connections\"; /ip firewall connection remove [find where connection-mark=WAN2-conn]"
interval=5s timeout=1sPings every 5 seconds with a 1-second timeout — much more aggressive than the built-in check-gateway probe, so failures are detected sooner.
down-script: connection removeDeletes existing conntrack entries for that WAN's connection-mark. This forces affected connections to be treated as "new" again on their next packet — triggering a fresh PCC hash that lands them on the still-alive WAN.
Tip Without the connection-remove step, existing long-lived connections (SSH sessions, streaming) stay marked to the dead WAN's connection-mark until they naturally time out — Netwatch's flush makes recovery near-instant for active sessions too, not just new ones.

Verification Commands

Run these after applying the configuration to confirm PCC is actually splitting traffic and failover behaves correctly.

Check connection marks are being applied
/ip firewall connection print where connection-mark!=""
Confirm routing table contents
/ip route print where routing-table=to-WAN1
/ip route print where routing-table=to-WAN2
Watch mangle rule packet counters increase
/ip firewall mangle print stats
Confirm gateway reachability status
/ip route print where check-gateway=ping
Force-test failover (unplug ether1, then watch)
/log print where topics~"route"
/tool netwatch print
Real Test, Not Just Config Review Open two browser tabs to a "what is my IP" site from two different LAN devices while both WANs are up — you should see two different public IPs, confirming PCC is actively splitting connections across both links.
